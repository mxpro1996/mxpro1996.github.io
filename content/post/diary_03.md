近期复盘了整条来时路，发现与其说这一路有清晰的阶段性划分，不如说它始终是一个从 2016 年开始、无限延续至今的兴趣课题。

真正的转变，其实是从被动接受到主动探索：不再盲从贴吧、Q 群以及 in189、天翼圈之类的论坛，被动等待别人投喂现成答案；而是开始自己做 MTK/QCOM/SPRD 平台移植，啃资料、做插桩、搞 ROM 适配，乃至逆向内核驱动。

这些东西放在今天看来，多少有点 GKI 之前的老黄历了。尤其是 Legacy HAL 那套东西，在一些老平台上，历史耦合和厂商私有接口简直是四面漏风。与其一直在旧系统里修修补补，倒不如借着 Treble 的接口边界，把硬件差异留在 vendor 侧，再用 GSI 验证通用 system/framework 层，不比继续给老黄历打补丁香吗？

AIDL/HIDL 这一套设计也让我想起 WDF。两者并不是同一种架构，但在工程思想上有相似之处：接口契约、模块化、调用方与实现方解耦，以及服务注册、发现和消息传递。很多东西最终都会走向这种模式——把具体功能拆成独立的实现单元，通过相对稳定的接口和消息体来组织协作，而不是让所有组件直接纠缠在一起。

以前曾经偏执地认为，非 CS/EE 不可，甚至到了有点无可救药的地步。现在回头看，才发现自己其实一直没有真正走出之前那个课题。

高安 ROOT 提取分析、Secure Boot 挖洞、内核驱动逆向……所谓的新阶段，很多时候不过是在延续旧课题的不同分支。当一项由兴趣驱动的长期任务，盖过了原本更长的职业主线，我才惊觉：自己或许并没有想象中那么向往这个行业。

这也算是一种祛魅。

将兴趣变成谋生手段，有时候是一件相当残忍的事情。很难说，究竟是什么心理，才能让一个人长期独自啃 DTSI，再拿着 IDA 把一个个 builtin 内核模块翻个底朝天。简而言之，自娱自乐。

有人会说：「赚钱嘛，不寒掺。」

这话当然没错。好歹耐着性子做下去，有一份能够维持生计的收入，也没什么不好。问题在于，实际工作究竟有多少真正值得投入的技术增量？

方案商每天做的，无非是一些 customization。工作流程本身真有那么多独到之处吗？

## 方案商的日常：从基线到 Feature

大致梳理一下，流程通常是这样的。

**1. 立项、SDK 与基线**

PM 提出立项，明确谈好的需求和功能范围。随后向原厂要 SDK，开出一套基线。

大家拿着 DEVKIT，先根据功能需求把基本能力调起来。硬件侧的 peer 则准备新的物料 BOM，参照原厂 Reference Design，对特定外设做调整。

**2. 硬件验证与初版样机**

硬件团队先把 NFFA、PSpice 等仿真跑起来，按照标准做完必要的测试，出一版初始硬件。

自动化夹具接着上场，DDR、UFS 以及其他外设做一轮基础测试。原厂的 initrd 也会先拿来启动，看看前级引导链路是否正常。

**3. Bring-up、工厂模式与 Feature 迭代**

硬件送到我们这里，开始做 Bring-up。

既然物料供应和参考设计早已定好，整套流程基本就是围绕既定基线展开。先用 FFBM/Factory Mode 之类的环境把 MMI 过一遍，粗略确认各项功能是否 Ready。送测团队负责后续的认证和测试，我们这边则围绕基线开发新的 Feature，再不断迭代合并，用原型机验证。

Feature 来来去去，大致是什么？

比如 Codec 内建方案效果不满意，要求外挂 I2S-PCM；做全景功能的，需要多 Path 录放，围绕 ALSA 或 AudioDevice 做 Mixer 融合和隔离；不同音频通路还要兼顾资源共享、状态管理和互不干扰。

做 CTS、基站场测的时候，现场一般就是收集 Dump 和 Log。至于返修或者一些棘手的系统 Bug，很多也是由更高层的研发人员利用 Dev 环境和前级引导手段抓取现场信息。

以前 Bugreport 不完善，问题定位经常需要售后也掌握一些基本的硬件调试能力，至少要会飞 UART、抓 Log。后来由于送检设备对调试接口的要求越来越严格，某些 JTAG 类型的接口也不能放得太显眼，最后只好藏在屏蔽罩下面。

UART 抓取复现过程，必要时接入 KGDB、KTrace 等调试手段；各家也都有自己的 Crash Dump 机制，收集回来的 Dump 再配合相应工具分析。

最优雅的方式，当然是拿匹配的 vmlinux 和 vmcore，用 crash 加载现场做交互式分析。否则就是通过 addr2line，结合 DWARF 调试信息，把地址还原到对应的源码位置。

**4. 外设与那些反复出现的问题**

LCM、TP、Codec，姑且算作三大件。其他外设的调试内容，其实千篇一律。

基线变化通常不大，尤其是在 GKI 之后。开局往往就是把既有的 Debug Framework 合并进来，处理 Hang、死锁，修复一些反复出现的 Crash 老毛病，完善现场信息捕获机制，尽量避免问题发生时丢失上下文。

有些时候，物料甚至已经在原型机阶段调好了，我们只需要接着往下做。

当然，原厂负责 ASIC/FPGA 的团队肯定比我们辛苦得多。我们多少还是站在巨人的肩膀上。

## AI 正在改变什么？

目前更值得关注的问题是：过去依靠封闭生态和 SoC 护城河建立起来的优势，正在受到 RK、树莓派等开放生态的冲击。

Allwinner（sunxi）虽然没有那么完整的开源底子，但社区生态一直相当活跃。公开域里有大量代码、文档、移植经验和可复用的实现，AI Agent 又能把这些已有资源的利用效率放大一截。

对于采用这些方案的 peer 来说，很多以前需要专门投入人力的功能，现在借助社区积累的实现和 AI 辅助，已经能够比较快地拼出一个能用的东西。

在同等竞争条件下，封闭方案的处境就未必那么有利了。

开放生态可以直接利用公开域留下的 snippet、文档和实现；而 Closed Source 导向的方案，往往还要先处理数据脱敏、模块解耦，甚至对语义和上下文做替换。某些场景下还不得不考虑本地部署。

但是，本地部署又有实际成本。小模型量化之后，可能也就胜任一下 snippet 检索、代码补全；大模型的推理成本、硬件资源和维护开销则众说纷纭。它不是一句「拥抱 AI」就能轻易解决的问题。

说到底，AI 对行业的影响，可以从供给侧和需求侧分别来看。

**需求侧的预期正在被 LLM 拉高。**

以前客户的诉求大致是：

「友司能搞，我们也要有。大家都要有技术，才能分到蛋糕，也要追求一些创新和首创。」

现在则逐渐变成：

「我问过 AI 了，它说这个行业内可行，而且还有一些特立独行的实现方式。」

客户不一定真的理解实现成本，但 AI 已经帮他们建立了一套新的功能预期。原本需要经过技术评估、方案论证才能提出的需求，现在可能只需要一句 Prompt 就能生成一份看起来相当完整的技术方案。

这自然会把需求侧的预期越抬越高。

**供给侧则必须提高 AI 的使用效率。**

你要是不在供给侧把 AI Power 拉满，应对起来就会很吃力。

比较理想的情况，是把 AI Coding、Code Reviewing、Testing 串成一条完整链路。原本 BSP 侧那些千篇一律的工作——例如文件系统和内存相关的合并、优化补丁，以及 Profiler 审计——理论上都可以借助 AI 提高效率。

例如，eBPF 本来已经有不错的性能观测和优化能力，但客户可能直接让 AI 许愿，要求做一个功能差不多的竞品。先不谈成熟度和实际交付能力，至少从概念到原型的距离已经被缩短了。

市场也正在为这种变化投票。

问题在于，过去很多工作本来就没有太多知识增量。它们更多是围绕既有基线做 customization、修 Bug、合补丁和适配物料。做得再熟练，也未必意味着积累了多少能够迁移的新知识。

我们总在谈论门槛被拉低，但有时候也应该看看，究竟是什么样的差异化，才真正值得投入。

成果导向的环境下，人们总是喜欢追逐地平线上那些看似马上就要到来的空中楼阁。

而真正的问题是：当实现成本被 AI 不断压低，过去依赖经验、封闭资料和人力堆出来的优势，还能维持多久？

不做音视频、不做 FOC 的团队，也能跨行业拼出一个大杂烩方案商了。

至于控制怎么搞定？

请阿拉丁神灯吧。

在 Linux 用户态开发中，std::thread 或 pthread 往往被视为并发的起点。但剥开库的包装，你会发现：用户态没有独立的并发物理权。

所有的同步原语，本质上都是从内核 UAPI 中“借”出来的执行策略。而 pthread，则是这套借贷契约的标准化搬运工。

一、 搬运工的本质：基于 Syscall 的逻辑装配

pthread（无论实现是 NPTL 还是 Musl）本身不创造“锁”，它只是将内核提供的原子能力与调度能力从 libc (System Call Interface) 中搬运并封装：

  1. 原子争抢 (Atomic)：利用硬件指令（ldrex/strex 或 cmpxchg）在用户态完成“快速路径”的无感拿锁。
  2. 系统调用 (Syscall)：当快速路径失败，它必须通过 sys_futex 向内核申请“认怂托管”。

审计结论：pthread 的逻辑，全靠从 libc 实现中获取必要的系统调用（Syscall）。

二、 借贷契约：从用户态到内核态的坍缩

在 Linux 这种“托管制”架构下，用户态线程（LWP）没有关闭抢占的权限。因此，同步逻辑必须由搬运工处理两套物理逻辑：

1. 快速路径：物理硬刚

在没有竞争时，pthread_mutex_lock 仅仅是一条用户态的原子指令。

  • 代价：几十个时钟周期。
  • 支撑：硬件缓存一致性协议。

2. 慢速路径：跨界求救 (Futex)

一旦冲突，搬运工意识到自己无法控制 CPU 核心（无法禁止抢占），便发起 syscall(SYS_futex, ...)。

  • 内核接管：内核将线程挂入 Wait Queue (WQ) 宿舍。
  • 代价：几千个周期。涉及上下文切换与调度器的介入。

三、 为什么 Cond Var 必须绑定 Mutex？

由于用户态没有“关中断”的物理特权，为了防止在“检查条件”后、“进入睡眠”前被踢下车（导致 Lost Wake-up），pthread 协议强制要求开发者使用 Mutex。

  • 逻辑本质：Mutex 是用户态的“虚拟中断开关”。
  • 执行深度：pthread_cond 是对 futex 的多次搬运，它是最沉重的同步原语，因为它注定要触发多次上下文切换。

四、 绕过“中间商”：直连 UAPI 的自由

既然 pthread 只是从 libc 拿了 Syscall 的搬运工，高性能架构（如 io_uring）选择直接对接内核工厂：

  1. 直接调用 Futex：跳过 libc 的官僚检查，自定义自旋策略。
  2. io_uring (异步 IO)：
    • 降维打击：不再为每个阻塞任务开线程，而是通过内核的 SQ/CQ 环形缓冲区实现数据流同步。
    • 绩效飞跃：彻底消灭了为了“等待”而产生的线程冗余。

五、 终极版图：并发原语的物理层次

层级 代表对象 行为本质 支撑力量
标准层 std::thread / pthread 契约搬运 libc 实现 (NPTL/Musl)
接口层 Futex / Clone 系统调用 (UAPI) 内核入口
内核层 Wait Queue 托管与精准唤醒 内核调度器
底层 Atomic 指令级硬刚 ldrex / strex

结语：lazurite 的并发哲学

用户态的并发库只是在代你行使那份“认怂保险”。

  • Atomic 是你的物理特权，让你在不惊动内核的情况下榨取性能。
  • Futex 是你的生存保单，它在你竞争失败时提供了一个安全（但昂贵）的避风港。

既然搬运工可以换，那么高性能编程的秘诀就在于：

尽可能在用户态解决战斗；如果非要认怂，请确保你直接对话内核（Syscall/io_uring），而不是在层层搬运的中间商手中耗尽 CPU 的热量。
